Now the SOLUTION:

The core fix: **never trust the summarizer blindly**. Validate and refuse.

Concretely:
1. **Template validation**: the summary must contain the required anchors (`## Objective` at minimum; ideally all section heads). If not → treat the compaction as failed: do NOT append CompactionEvent, do NOT slide cpr_start, return False (so the loop keeps the valid window). Retry next turn (or force one corrective retry).
2. **Echo/verbatim detection**: reject a "summary" that is a near-copy of the transcript tail or that equals a slice of the serialized history (the lab's scenario B echo).
3. **Don't let a bad prior summary poison the next**: when the prior summary fails validation, don't feed it as `<prior-summary>` (or mark it as untrusted). Better: since we're now refusing to store bad summaries, the chain breaks naturally.
4. **Make the compaction call structurally different from an agent turn**:
   - Send `tools=None` (already) AND make the client NOT parse tool calls when tools weren't requested (so any tool-call markup is at least visible/ignorable rather than silently dropped in a confusing way). Actually more importantly: pass an explicit system message that pins the summarizer role (currently there's NO system prompt for the compaction call).
   - Consider `tool_choice="none"` / explicitly telling the model it has no tools.
   - Force non-streaming for compaction? Not necessary.
5. **Separate the "currently in-flight assistant turn" from the material to summarize.** Looking at the three cases, the summary text closely resembles what the agent was ABOUT to do — i.e., the tail of the window. Feeding the model a transcript that ends mid-action invites "continue" behavior. Trimming/anchor: end the transcript, and label it clearly as a closed, past conversation (e.g., wrap in `<conversation>...</conversation>` — which the template already does — but also add "the conversation has ENDED; do not continue it").
6. **Observability**: record whether a summary was validated; count dropped non-text events; log a warning when a summary is rejected or looks like an echo.
7. **Degradation policy**: if compaction repeatedly fails validation, what then? Options: (a) keep the window and hope the main model can handle it (may blow the context); (b) fall back to a deterministic "extractive" summary (e.g., keep the first user message + the last N tool results + the file list) so we never lose the objective. (b) is attractive: a deterministic fallback guarantees the requirement survives even when the model misbehaves.

Also, an important subtlety: if we refuse a bad summary, `compact()` returns False and the loop proceeds with the (over-window) `msgs`. If the window truly exceeds the model window, the LLM call will fail with `context_window_exceeded` → the loop calls `compact()` again → fails again → raises. So refusing must be paired with a fallback that ALWAYS produces a valid summary (deterministic extractive), otherwise a misbehaving model bricks long sessions. So the recommended design:

```
summary, chars = self._summarize(...)
if not self._valid(summary):
    summary = self._extractive_fallback(window)   # deterministic, guaranteed to carry the objective
self.log.append(CompactionEvent(summary=summary))
```

The extractive fallback: e.g., "## Objective\n- <first user message>\n\n## Work State\n### Active\n- <last assistant text>\n\n## Relevant Files\n- <_recent_working_files>". That always carries the objective.
